## 来源

用户提供的 4号真实 AI 助手产品与技术方案，时间：2026-07-03。

## 总体判断

这份方案方向正确，可以作为后续真实 AI 助手的产品蓝图和技术边界参考。

核心结论：

1. 不再做本地规则式假 AI。
2. AI 助手入口可以预留，但真实 API 未接入前不开放对话能力。
3. AI 第一版定位为：当前知识点解释助手、现场检查提醒助手、学习路径引导助手。
4. 前端不直接调用 Claude API，必须走后端代理。
5. 前端不保存 API Key，不传整个知识库。
6. 系统提示词必须强调安全边界，不承诺加工安全。
7. 后端必须做二次安全校验。
8. 输出应为结构化 JSON，便于前端分块展示。

## 可采纳内容

### 1. AI 能力边界

第一版允许：

- 解释当前知识点。
- 说明使用场景。
- 提醒易错点。
- 基于真实 relatedIds / relatedEntries 推荐相关知识。
- 解释参数工具结果含义。
- 输出现场检查清单。

第一版禁止：

- 生成危险最终加工参数。
- 承诺“不会撞机”“可以直接跑”。
- 替用户做最终工艺决策。
- 回答和数控无关问题。
- 编造知识库不存在的内容。

### 2. 接口方向

推荐接口：

```text
POST /api/ai/detail-assistant
```

第一版前端请求应尽量精简：

```json
{
  "entryId": "learn-coordinate-system",
  "question": "现场怎么检查 G54 有没有设错？",
  "conversation": [],
  "toolContext": null
}
```

后端负责补齐：

- 当前知识点。
- 少量相关条目。
- quickCheck。
- relatedIds。
- 用户模式。
- 风险等级。
- 是否允许 AI 回答。

### 3. 系统提示词方向

可采纳原则：

- 身份：数控工程师助手。
- 风格：简洁、专业、现场化。
- 输出：结论、步骤、风险、检查项。
- 安全：不承诺安全，必须现场验证。
- 新手模式：多解释、多比喻、少缩写。
- 老手模式：少废话、重格式、重风险和检查项。

### 4. UI 方向

可采纳：

- 详情页右下角预留“问 AI”。
- 未接入真实 API 前显示“AI 助手接入中”。
- 预设问题：这个怎么用？有什么易错点？现场怎么检查？
- AI 回答按模块展示，不显示一大段纯文本。
- 面板底部固定安全提醒。

### 5. 安全拒答方向

必须拒答或转安全替代方案：

- 要求最终转速进给。
- 要求保证程序安全。
- 要求跳过检查。
- 要求绕过安全门或保护。
- 非数控问题。
- 要求编造资料。

## 需要修正的地方

### 1. 不建议前端直接传完整 entry

4号方案里前端传完整 entry，长期看不够安全。

推荐改为：

- 第一版为了静态站过渡，可以传当前 entry 摘要。
- 正式后端版必须只传 entryId。
- 后端根据 entryId 查当前知识点和关联条目。

### 2. 不建议前端传 model / temperature

模型、温度、max_tokens、缓存策略必须由后端控制。

### 3. Claude Opus 4.7 参数要更新

后续如果接 Claude API，默认模型建议：

```text
claude-opus-4-7
```

复杂问题建议：

```json
"thinking": { "type": "adaptive" }
```

Opus 4.7 不应继续使用旧式固定 thinking budget。

### 4. 结构化返回要作为强约束

后端返回前端建议统一为：

```json
{
  "answerType": "detail_explanation",
  "conclusion": "",
  "steps": [],
  "risks": [],
  "checklist": [],
  "safetyNote": "",
  "relatedIds": [],
  "blocked": false,
  "blockReason": null,
  "confidence": "medium"
}
```

### 5. 第一阶段只做占位，不开放问答

当前项目还没有真实后端代理和安全二次校验，所以不能上线“可提问”的 AI 面板。
