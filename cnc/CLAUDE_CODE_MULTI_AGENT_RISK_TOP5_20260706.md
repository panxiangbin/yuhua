# 本轮多AI协作最关键的5个风险点（20260706）

1. **3号建议删除的两个文件不是空文件，误删会造成真实损失**
   `entry-to-images-map.js`实测有415条图片映射数据（变量名是`ENTRY_TO_IMAGES_MAP`，不是3号说的`CNC_ENTRY_TO_IMAGES_MAP`），`knowledge-gallery.js`实测是一个功能完整的图片轮播组件代码，都不是3号判定的"空文件/垃圾文件"。**如果Codex没看到这份验收报告，直接按3号建议执行删除，会造成不可逆的真实损失。**

2. **`search_alias_dictionary.json`目前无法被程序直接读取（语法错误）**
   第212行一处多余逗号导致`JSON.parse`直接报错，整个211+条数据在修复这一个字符之前**完全无法被任何代码加载使用**。虽然0号自己标注过"字段缺失"，但没有说清楚这会导致整体解析失败，如果有人以为"只是几条数据缺字段，问题不大"而直接接入代码，会遇到运行时崩溃。

3. **4号的"新12关课程"和线上实际12关几乎是两套不同内容，容易被误执行成整体替换**
   已逐条对照过，4号提议的12关标题和`index.html`里当前真实运行的12关标题重叠但顺序打乱，且各有对方没有的独有主题。如果Codex把4号的方案当作"填空任务"直接派工，实际做出来的会是"整个换掉现有12关"，和"保留现有12关、不推倒重做"这条既定要求直接矛盾。

4. **6号的公网迁移方案建立在"项目已确定部署阶段"的假设上，但项目目前还在本地跑**
   `Cloudflare Pages+Access+R2`方案本身技术选型没问题，但当前项目实际状态是本地用`python -m http.server`跑起来测试，尚未正式部署到任何公网平台。如果直接按6号的"现在（本周~2周）"阶段清单派工（比如"审计并配置Cloudflare Access"），会发现根本没有对应的Cloudflare项目可审计，容易造成派工目标落空。

5. **`app.js`的`getEntryText()`函数会把`entry.source`路径文本混入搜索匹配范围（3号发现，我已独立验证）**
   实测178条知识条目里168条（94%）的`source`字段含有"04_数控知识库 / 编程基础"这类目录文本，这些文本会被拼进每条搜索用的文本里参与关键词匹配。这意味着现有搜索功能存在一个从未被之前几轮审计发现的隐藏误命中风险点，值得在下一轮"补全在线12关映射"或"接入0号新数据"之前，先评估要不要把`entry.source`从`getEntryText()`的拼接字段里移除。
