## 🔍 与0号方案的冲突分析

### 0号方案回顾
- **位置**: `data.js` 中每个条目的 `aliases` 字段
- **类型**: 数据层别名
- **示例**: 
  ```javascript
  { 
    code: "G02",
    aliases: ["G2", "圆弧插补", "顺时针"],
    ...
  }
  ```

### 1号方案（本方案）
- **位置**: `search-aliases.js` 独立文件
- **类型**: 搜索层扩展
- **工作方式**: 在用户输入后、匹配之前进行词项扩展

### 冲突评估结果

**✅ 无直接冲突**

#### 原因：
1. **作用层不同**
   - 0号：数据属性层（每个条目的固有属性）
   - 1号：搜索逻辑层（输入词的动态扩展）

2. **触发时机不同**
   - 0号：在 `getEntryText()` 中被读取并拼接到搜索文本中
   - 1号：在用户输入后，通过 `expandSearchTerm()` 预处理

3. **可以共存**
   - 用户输入 "G2" → 1号扩展为 ["G2", "G02", "圆弧插补", "顺时针圆弧"]
   - 这些扩展词去匹配条目的 title/code/summary/**aliases** 字段
   - 0号的 aliases 字段依然有效，作为匹配目标的一部分

#### 潜在协同效应：
- 1号负责"用户不知道标准词怎么说"的场景（口语→标准）
- 0号负责"条目本身有多个别名"的场景（数据完整性）
- 两者形成互补：**输入侧扩展 + 数据侧完备**

## 💡 方案保留建议

### 推荐策略：**双轨并行，各司其职**

#### 短期（当前阶段）
**保留 1号（search-aliases.js）为主**

**理由：**
1. ✅ 立即可用，无需改动42K+本地知识库
2. ✅ 集中管理，易于快速迭代和调整
3. ✅ 适合应对"新手不知道怎么搜"的痛点
4. ✅ 可以通过日志分析用户搜索习惯，快速补充高频误搜词

**适用场景：**
- 用户输入口语化词汇（"快移" "撞机"）
- 简写查询（"G2" "G54"）
- 跨类别联想（"对刀"→"G54"+"寻边器"）

#### 长期（知识库完善后）
**0号（data.aliases）作为数据层基础设施**

**理由：**
1. 数据内聚：每个条目的别名属于条目本身的属性
2. 易维护：新增条目时直接填写 aliases 字段
3. 标准化：符合结构化数据管理规范

**实施路径：**
1. 在知识库批量导入时，根据 search-aliases.js 的映射规则自动生成每个条目的 aliases 字段
2. 将 1号的30组映射"下沉"到数据层
3. search-aliases.js 转为"临时补丁文件"，只保留尚未下沉的新增别名

#### 最终形态（理想态）
**1号 + 0号 混合架构**

```
用户输入 "G2"
  ↓
1号：搜索层快速扩展（口语、简写、热门误搜）
  ↓ ["G2", "G02", "圆弧插补"]
  ↓
匹配引擎：对所有条目进行匹配
  ↓
0号：数据层 aliases 参与匹配（条目固有别名）
  ↓
返回结果
```

**优势：**
- 搜索层（1号）：灵活、快速迭代、应对新场景
- 数据层（0号）：稳定、标准化、内聚完整

## 📝 技术备注

### 性能评估
- **当前规模**: 30组映射，查询时间 <1ms
- **扩展到100组**: 预计仍 <5ms（数组查找 + 文本拼接）
- **不影响渲染**: 搜索扩展在用户输入时触发，不阻塞页面加载

### 兼容性
- **ES6+**: 使用 `find`/`flatMap`，需要现代浏览器（Chrome 45+, Firefox 40+）
- **降级方案**: 可改用 ES5 语法（for循环 + concat）

### 维护建议
- 每次新增别名时注明来源（用户反馈/日志分析/专家建议）
- 定期清理低效映射（扩展后仍无匹配结果的别名）
- 版本化管理（每次重大更新保留历史版本备份）
