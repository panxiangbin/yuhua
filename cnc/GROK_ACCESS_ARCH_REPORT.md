## 1. 当前方案评估

### 当前前端邀请码方案的优点
- **部署简单**：完全依赖 GitHub Pages 静态托管，无需额外服务器或后端配置，用户无需运维。
- **零成本**：免费使用 GitHub Pages，适合当前内容规模。
- **快速迭代**：前端直接实现邀请码验证，修改代码即可更新授权逻辑，便于快速测试。
- **现有机制**：已有邀请码/授权链接基础，易于小范围分发给授权用户。

### 当前方案的根本缺陷
- **安全性薄弱**：访问控制完全在前端实现，任何懂浏览器 DevTools 或网络抓包的用户都能绕过邀请码，直接访问静态资源（HTML/JS/JSON 数据文件）。
- **非真正权限控制**：无法实现管理员集中管理用户列表，无法追踪访问记录或动态吊销授权。
- **长期风险高**：随着数控资料内容价值提升（G-code、工艺参数、教学视频等），公开泄露风险增大，前端控制无法满足“只有授权用户能看”的强需求。
- **扩展性差**：内容增多后，静态文件体积增大，维护授权逻辑复杂化，不适合长期稳定公网版。

## 2. 三条路线对比表

| 维度             | 路线 A: 静态站 + 前端邀请码 | 路线 B: 静态站 + Cloudflare Access | 路线 C: 轻后端权限系统 (Vercel/Workers 等) |
|------------------|-----------------------------|------------------------------------|-------------------------------------------|
| **安全性**      | 低（前端可绕过）           | 高（Cloudflare 边缘层认证）       | 高（后端/数据库验证）                     |
| **稳定性**      | 高（GitHub Pages 可靠）    | 高（Cloudflare 全球 CDN + Zero Trust） | 中高（依赖平台，但可控）                 |
| **成本**        | 免费                       | 免费层足够（Access 基础免费）     | 低（Vercel/Workers 免费阶梯）            |
| **实现难度**    | 最低（已部分实现）         | 中（配置 Cloudflare）             | 中（需轻后端）                            |
| **后续维护成本**| 低（前端改动）             | 低（Cloudflare 仪表盘管理）       | 中（需维护授权逻辑/用户表）              |
| **适合当前项目阶段** | 短期过渡，不适合长期      | 非常适合（静态 + 强保护）         | 适合未来扩展，但当前略重                 |

## 3. 最终推荐方案

**首推路线 B：静态站 + Cloudflare Access**

**原因**：
- 完美匹配项目“静态站 + GitHub Pages + 内容资料站 + 授权查看”的场景：无需改变核心静态托管，只在前端（GitHub Pages）前加 Cloudflare 保护层，实现真正“管理员控制谁能看”的 Zero Trust 访问。
- 安全性大幅提升：Cloudflare Access 使用 JWT / 邮箱 / SSO 等方式验证，边缘执行，无法被前端绕过。
- 用户体验好：授权用户通过 Cloudflare 登录/邀请链接访问，无需复杂部署；管理员在 Cloudflare 仪表盘轻松管理用户/组/策略。
- 长期稳定：Cloudflare 全球网络，免费层覆盖小规模使用，适合数控资料持续扩充。
- 对比 A：解决前端弱点；对比 C：无需引入后端/数据库，保持轻量，运维门槛最低。
- 结合用户偏好：不想折腾复杂运维，此方案最简单可靠。

## 5. 对当前项目文件层的影响

采用推荐路线 B 后：
- **前端**：最小影响。移除或弱化当前邀请码 JS 逻辑（保留作为 fallback）。静态文件（HTML/JS/CSS/JSON 参数数据）无需大改。
- **域名 / CDN**：需通过 Cloudflare 代理 GitHub Pages（设置 CNAME 或 Workers 路由）。如果无自定义域名，可直接保护 GitHub.io 地址。
- **授权逻辑**：从前端 JS 迁移到 Cloudflare Access 策略（仪表盘配置，无代码改动）。
- **部署方式**：保持 GitHub Pages 部署流程不变，只增加 Cloudflare 配置步骤。CI/CD 无影响。

整体改动小，静态本质不变。
