### 🔴 Sev-1（严重，阻断核心功能）

#### 问题1：学习卡片系统 100% 失效——无限递归导致调用栈溢出
- **文件位置**：`app.js` 第1967-1971行
- **复现步骤**：
  1. 打开 `http://localhost:8791/index.html#study`
  2. 点击任意一张学习卡片（12张，含理论上应精确匹配的第4关"告诉机床活儿在哪"）
  3. 或用Tab聚焦到卡片后按Enter
- **现象**：无论点击哪一张卡片，页面都停留在原视图，`#detail-title`保持"选择左侧条目查看详情"默认文案，没有任何跳转。直接在控制台调用底层匹配函数会看到：
  ```
  RangeError: Maximum call stack size exceeded
      at normalizeCompactText (http://localhost:8791/app.js:1968:3)
      at normalizeCompactText (http://localhost:8791/app.js:1968:10)
      ...（无限重复）
  ```
- **根因**：
  ```js
  function normalizeCompactText(text) {
    return normalizeCompactText(text)   // ← 自己调自己，从未真正执行标准化逻辑
      .replace(/\s+/g, '')
      .replace(/[：:，,。.!！?？"“”'‘’（）()【】\[\]-]/g, '');
  }
  ```
  这个函数体第一行调用了自己而不是做实际的文本转换（对比文件里另一个正常的同类函数`normalizeText`，正常写法应该是先做`String(text||'').toLowerCase()`之类的基础转换，而不是递归调用同名函数）。这个函数被 `findStudyRuleByCardTitle()`（1991/1994行）和 `findKnowledgeItemByRule()`（2021/2033行）调用——这两个函数正是12张学习卡片点击链路的核心，所以**每一次点击都会立即栈溢出**，和卡片标题是否匹配规则无关。
- **影响范围**：仅限学习卡片匹配链路，不影响主搜索（主搜索用的是另一个正常的`normalizeText`函数，已在任务4验证完好）。
- **修复建议**：把函数体第一行改成基础转换而不是自调用，例如：
  ```js
  function normalizeCompactText(text) {
    return String(text || '').toLowerCase()
      .replace(/\s+/g, '')
      .replace(/[：:，,。.!！?？"“”'‘’（）()【】\[\]-]/g, '');
  }
  ```

#### 问题2：`#gallery` 路由触发未捕获异常，打断 `bootstrap()` 剩余初始化步骤
- **文件位置**：`app.js` 第164行（`dom.galleryGrid`）+ 第1201/1247行（`renderGallery`/`renderGalleryRich`）
- **复现步骤**：
  1. 整页打开 `http://localhost:8791/index.html#gallery`（必须是硬刷新直达，不能页内跳转）
  2. 对比同样方式打开 `#calculator` 作为对照组
- **现象**（实测对比）：

  | 检查项 | `#gallery` | `#calculator`（对照组） |
  |---|---|---|
  | `#rpm-result` 文案 | "结果显示在这里"（未计算） | "建议转速约 764 rpm"（已计算） |
  | `#knowledge-pill` 文案 | "知识库待加载"（未自动加载） | "核心知识包已接入"（已加载） |
  | `.view.active` | `view-gallery`（视图本身切对了） | `view-calculator` |

  另外，中途通过侧边栏点击"🖼 图片图库"按钮（页面已完全加载完毕之后再点）也会触发同样的崩溃：点击后**侧边栏不会自动关闭**（应该关闭）、**URL hash不会同步成`#gallery`**（应该同步），因为这两步都写在`navigate()`函数里`renderGalleryRich()`调用之后，异常发生后这两行代码不会被执行到。
- **根因**：`dom.galleryGrid`（第164行）指向`document.querySelector("#gallery-grid")`，但当前`index.html`里图库视图的容器id已经改成了`#cncGalleryGrid`（图库功能被重新设计过，改用独立脚本`gallery-featured.js`管理），`#gallery-grid`这个id已经不存在。`renderGallery()`/`renderGalleryRich()`两个函数里`dom.galleryGrid.innerHTML = ...`（1201/1247行）没有判空保护，直接对`null`赋值，抛出`TypeError: Cannot set properties of null (setting 'innerHTML')`。
- **影响范围**：直接分享`#gallery`链接打开的用户，会静默丢失：参数计算器初始值、知识库核心包自动加载、知识地图/推荐系统/首页精选图初始化（`initEnhancedFeatures()`整体不执行）。侧边栏点击图库按钮的用户，会遇到侧边栏卡住不关闭的体验问题。
- **修复建议**：`renderGallery()`/`renderGalleryRich()`这两个函数目前渲染的`#gallery-grid`已经被`gallery-featured.js`管理的`#cncGalleryGrid`完全取代（功能重复），建议直接删除这两个函数以及`navigate()`里`if (view === "gallery") renderGalleryRich();`这一行，而不是给`dom.galleryGrid`加判空——因为加判空只能让它不崩溃，但函数本身渲染的内容现在已经没有对应容器可以显示了，是彻底的死代码。

## 未验证事项声明

- **移动端"滚动流畅度"（问题5的"首页滚动流畅度"要求）未做真实验证**——这是主观体验指标，需要真机或至少真实的触摸/滚轮事件配合帧率采样，本工具的`preview_eval`/DOM测量无法测出"流畅"与"卡顿"的主观差异，只能证明布局本身没有横向溢出等结构性问题。
- **本轮截图工具（`preview_screenshot`）在两个不同的预览服务器实例上均30秒超时**，未能获取任何真实截图作为视觉证据，全部移动端结论基于精确DOM测量（`getBoundingClientRect`/`scrollWidth`/`getComputedStyle`），足以证明布局尺寸类问题，但**无法证明纯视觉层面的问题**（比如配色是否协调、图标是否清晰、动画是否顺滑）。
- **iPhone 12/13/14 三档机型的具体像素差异未逐一测试**，本轮只测了390×844（近似iPhone 12/13/14标准款）和414×896（近似iPhone 12/13/14 Plus/Pro Max）两档，没有做三个精确机型的独立测试，因为它们的CSS视口宽度实际上高度重合（iPhone 12/13/14标准款都是390px，Pro Max都是428px左右，本轮用414px做了近似）。
- **未测试真实触摸手势**（如实际手指滑动"最近查看"横向区），只验证了`overflow-x:auto`且内容确实超宽（结构上具备可滑动条件），未用触摸事件模拟真实划动交互。
- **`#gallery`崩溃对`gallery-featured.js`自身管理的`#cncGalleryGrid`内容渲染没有影响**（该脚本独立运作，20张图片正常显示），本报告里"#gallery崩溃"specifically指`app.js`里`renderGalleryRich()`那条独立、失效的渲染分支，不代表用户在图库页看到的画面是空白的——这一点在问题2描述里已经说明，此处再次强调避免误读。
